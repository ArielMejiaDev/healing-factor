X-Factor Documentation

A self-healing Laravel package that catches exceptions and automatically creates pull requests with fixes using AI CLI tools (Claude Code, OpenCode).

Requirements

  • PHP 8.4+
  • Laravel 11 or 12
  • CLI driver: Claude Code or OpenCode CLI installed on the server
  • API driver: Only an ANTHROPIC_API_KEY (no CLI installation needed)
  • GitHub CLI (gh) installed and authenticated (for PR creation)
  • A queue worker running (recommended for production)

Installation

1. Install via Composer

composer require arielmejiadev/x-factor

2. Run the install command

php artisan x-factor:install

This will:

  • Publish the config file (config/x-factor.php)
  • Publish the migration
  • Run the migration (with confirmation)
  • Verify that the CLI tool (claude or opencode) is available
  • Check that ANTHROPIC_API_KEY is set

3. Add environment variables to .env

# Required
ANTHROPIC_API_KEY=sk-ant-...

# Optional — all have sensible defaults
X_FACTOR_ENABLED=true
X_FACTOR_DRY_RUN=false
X_FACTOR_DRIVER=cli
X_FACTOR_CLI_TOOL=claude
X_FACTOR_MODEL=
X_FACTOR_MONITOR=nightwatch
X_FACTOR_WEBHOOK_PATH=x-factor/webhook
X_FACTOR_WEBHOOK_SECRET=your-webhook-secret
X_FACTOR_PROCESS_TIMEOUT=3600
X_FACTOR_MAX_TURNS=25
X_FACTOR_DEBOUNCE_MINUTES=5
X_FACTOR_RETENTION_DAYS=30
X_FACTOR_LOG_CHANNEL=x-factor
X_FACTOR_QUEUE_CONNECTION=
X_FACTOR_QUEUE_NAME=
X_FACTOR_GITHUB_PAT=

4. Start the queue worker

php artisan queue:work --timeout=3700

The timeout should exceed the configured process timeout (default 3600s) to avoid the worker killing jobs prematurely.

Why APP_ENV=staging? X-Factor only runs in production and staging by default. In local, errors are expected during active development — X-Factor is designed for bugs that slip through to staging or production.

Why no ANTHROPIC_API_KEY for CLI? Claude Code handles its own authentication. The API driver calls the Anthropic API directly, so it needs the key.

How It Works

  1. An exception occurs in your Laravel app.
  2. X-Factor captures it via a webhook (from Nightwatch or Bugsnag) or the built-in exception listener.
  3. The exception is fingerprinted, debounced, and deduplicated.
  4. A queued job creates an isolated git worktree on a new branch — your production working directory is never touched.
  5. The CLI tool (Claude Code or OpenCode) runs inside the worktree with a prompt describing the issue.
  6. The AI analyzes the code, writes a fix, commits, pushes, and opens a draft pull request.
  7. The worktree is automatically cleaned up (even if the CLI fails).
  8. You review the PR and merge.

Configuration

All configuration lives in config/x-factor.php. Every key can be overridden via environment variables.

Master Switch

'enabled' => env('X_FACTOR_ENABLED', true),

Set to false to disable all processing. Webhooks will still return 200 but won't create issues.

Environment Whitelist

'environments' => ['production', 'staging'],

X-Factor only processes exceptions in these environments. Set to an empty array [] to allow all environments.

Dry Run

'dry_run' => env('X_FACTOR_DRY_RUN', false),

When enabled, X-Factor logs what it would do but never executes the CLI tool. Useful for testing your setup.

Driver

'driver' => env('X_FACTOR_DRIVER', 'cli'),
  • cli — Runs Claude Code or OpenCode as a subprocess. Requires the CLI tool installed on the server.
  • api — Calls the Anthropic Messages API directly with tool_use. No CLI installation required — ideal for staging/production servers (DigitalOcean, Laravel Cloud, AWS).

CLI Tool

'cli_tool' => env('X_FACTOR_CLI_TOOL', 'claude'),
  • claude — Uses Claude Code (claude -p ...).
  • opencode — Uses OpenCode (opencode run ...).

AI Model

'model' => env('X_FACTOR_MODEL', null),

Override the default model. When null, the CLI tool picks its own default.

Process Settings

'process' => [
    'timeout' => (int) env('X_FACTOR_PROCESS_TIMEOUT', 3600),
    'max_turns' => (int) env('X_FACTOR_MAX_TURNS', 25),
    'working_directory' => null,
],
  • timeout — Maximum seconds the CLI process can run (default: 1 hour).
  • max_turns — Maximum AI conversation turns (Claude Code only).
  • working_directory — Base git repository path. null defaults to base_path(). The git worktree is created from this directory.

Git Worktree Isolation: When resolving an issue, X-Factor creates a temporary git worktree on a dedicated branch. The CLI tool runs exclusively inside this worktree, so your production working directory is never modified. The worktree is automatically removed after the CLI finishes — even if the process fails.

Pull Request Settings

'pr' => [
    'draft' => true,
    'labels' => ['x-factor', 'auto-fix'],
    'reviewers' => [],
    'branch_prefix' => 'x-factor/fix',
],
  • draft — Create PRs as drafts (recommended for safety).
  • labels — Labels applied to every PR.
  • reviewers — GitHub usernames to request review from.
  • branch_prefix — Branch names follow the pattern {prefix}-{slug}-{random}.

Queue

'queue' => [
    'connection' => env('X_FACTOR_QUEUE_CONNECTION', null),
    'name' => env('X_FACTOR_QUEUE_NAME', null),
],

Customize the queue connection and name. null uses your app defaults. Consider using a dedicated queue to avoid long-running resolution jobs from blocking other work.

API Keys

'api_keys' => [
    'anthropic' => env('ANTHROPIC_API_KEY'),
    'github_pat' => env('X_FACTOR_GITHUB_PAT'),
],
  • anthropic — Passed to the CLI tool as ANTHROPIC_API_KEY environment variable.
  • github_pat — Passed to the CLI tool as GITHUB_TOKEN so gh pr create works in environments without interactive gh auth login.

Go to GitHub → Settings → Developer settings → Fine-grained tokens and create a token with these permissions:

Monitor Strategy

X-Factor supports one active monitor at a time.

'monitor' => env('X_FACTOR_MONITOR', 'nightwatch'),

Nightwatch

Set X_FACTOR_MONITOR=nightwatch.

Configure your Laravel Nightwatch project to send webhooks to your X-Factor endpoint. X-Factor processes issue.opened and issue.reopened events.

Expected webhook payload

{
    "event": "issue.opened",
    "payload": {
        "organization_id": "org-123",
        "application_id": "app-456",
        "environment": { "id": "env-789" },
        "issue": {
            "title": "ErrorException: Undefined variable $foo",
            "exception_class": "ErrorException",
            "message": "Undefined variable $foo",
            "stacktrace": "#0 /app/Http/Controllers/..."
        }
    }
}

Signature verification: HMAC-SHA256 over the raw request body. The computed hash is compared against the X-Nightwatch-Signature or X-Webhook-Signature header.

Bugsnag

Set X_FACTOR_MONITOR=bugsnag.

Configure a Bugsnag webhook pointing to your X-Factor endpoint. X-Factor processes exception and firstException triggers.

Expected webhook payload

{
    "trigger": "exception",
    "error": {
        "exceptionClass": "RuntimeException",
        "message": "Something went wrong",
        "stackTrace": "..."
    }
}

Signature verification: Bearer token in the Authorization header, compared against the configured secret.

Exception Listener

Set X_FACTOR_MONITOR=exception_listener.

No webhook needed. X-Factor listens to Laravel's MessageLogged (error/critical level) and JobExceptionOccurred events directly. Every unhandled exception is captured.

The exception listener includes a recursion guard to prevent infinite loops if X-Factor's own operations trigger exceptions.

Webhook Setup

Endpoint

POST /x-factor/webhook

The path is configurable:

'webhook' => [
    'path' => env('X_FACTOR_WEBHOOK_PATH', 'x-factor/webhook'),
    'secret' => env('X_FACTOR_WEBHOOK_SECRET'),
    'middleware' => [],
],

Signature Verification

Set X_FACTOR_WEBHOOK_SECRET to a strong random string. Share this secret with your monitor service.

  • Nightwatch: HMAC-SHA256 of the request body compared against the X-Nightwatch-Signature header.
  • Bugsnag: Authorization: Bearer {token} header compared against the secret.

If X_FACTOR_WEBHOOK_SECRET is not set, signature verification is skipped (a warning is logged).

Additional Middleware

'webhook' => [
    'middleware' => [\App\Http\Middleware\CustomMiddleware::class],
],

CSRF verification is automatically excluded from the webhook route.

Exception Categories

Categories let you customize AI behavior per exception type:

'categories' => [
    'quick_fixes' => [
        'cli_tool' => 'claude',
        'model' => null,
        'timeout' => 1800,     // 30 minutes
        'max_turns' => 15,
        'prompt' => null,       // null = use default prompt
        'exceptions' => [
            \ErrorException::class,
            \TypeError::class,
        ],
    ],
    'complex_fixes' => [
        'cli_tool' => 'claude',
        'model' => null,
        'timeout' => 3600,     // 1 hour
        'max_turns' => 30,
        'prompt' => null,
        'exceptions' => [
            \LogicException::class,
            \RuntimeException::class,
        ],
    ],
],

Each category can override: cli_tool, model, timeout, max_turns, and prompt. Exceptions not matching any category use the top-level defaults.

Custom Prompts

// Per category
'categories' => [
    'quick_fixes' => [
        'prompt' => 'Fix this {exception_class} in the Laravel app: {exception_message}. Branch: {branch_name}',
    ],
],

// Global fallback
'prompt' => 'You are debugging a Laravel app. Fix: {title}',

Ignored Exceptions

Exceptions that should never be processed (infrastructure issues, unfixable errors):

'ignored_exceptions' => [
    \OutOfMemoryError::class,
    \Illuminate\Http\Exceptions\ThrottleRequestsException::class,
    \Symfony\Component\HttpKernel\Exception\HttpException::class,
    \Illuminate\Session\TokenMismatchException::class,
],

Add your own exception classes to this array.

Deduplication

X-Factor uses three layers of deduplication to prevent processing the same exception multiple times:

  1. Cache Debounce — Same fingerprint is rejected within the debounce window (default: 5 minutes).
  2. Database Check — If an issue with the same fingerprint is already pending or resolving, the new one is skipped.
  3. Unique Constraint — The (fingerprint, status) database constraint prevents duplicates at the DB level.
'debounce_minutes' => (int) env('X_FACTOR_DEBOUNCE_MINUTES', 5),

Artisan Commands

x-factor:install

Publishes config and migration, runs migration, verifies setup.

php artisan x-factor:install

x-factor:status

Displays a table of issues with summary statistics.

php artisan x-factor:status
php artisan x-factor:status --limit=50

x-factor:retry {id}

Retries a failed issue by resetting it to pending and dispatching it again.

php artisan x-factor:retry 42

x-factor:prune

Deletes resolved and failed issues older than the retention period. Also recovers any issues stuck in resolving status beyond the process timeout.

php artisan x-factor:prune
php artisan x-factor:prune --days=7

x-factor:recover-stale

Finds issues stuck in resolving status beyond the configured process timeout and marks them as failed. Failed issues can then be retried from the dashboard or via x-factor:retry.

php artisan x-factor:recover-stale
php artisan x-factor:recover-stale --minutes=90

Recommended Schedule

Add both commands to your routes/console.php to keep the issues table healthy:

use Illuminate\Support\Facades\Schedule;

// Recover stuck resolving issues every hour
Schedule::command('x-factor:recover-stale')->hourly();

// Prune old resolved/failed issues daily
Schedule::command('x-factor:prune')->daily();

recover-stale runs hourly to catch stuck issues quickly. prune runs daily for general cleanup. Both are idempotent and safe to run at any frequency.

x-factor:test

Creates a test issue and dispatches it for resolution. Useful for verifying your setup.

php artisan x-factor:test
php artisan x-factor:test --exception=RuntimeException
php artisan x-factor:test --sync   # Run synchronously (no queue)

Events

X-Factor fires events at each stage of the resolution lifecycle:

EventFired WhenProperties
IssueCreatedIssue is created from webhook or exceptionIssue $issue
IssueResolvingResolution starts (status → resolving)Issue $issue
IssueResolvedResolution succeeds (status → resolved)Issue $issue
IssueResolutionFailedResolution fails (status → failed)Issue $issue, string $reason

Example: Send a Slack notification on resolution

use ArielMejiaDev\XFactor\Events\IssueResolved;

Event::listen(IssueResolved::class, function (IssueResolved $event) {
    Notification::route('slack', config('services.slack.webhook'))
        ->notify(new IssueFixedNotification($event->issue));
});

Logging

'log_channel' => env('X_FACTOR_LOG_CHANNEL', 'x-factor'),

If the channel doesn't exist in config/logging.php, X-Factor auto-configures it:

  • Driver: daily
  • Path: storage/logs/x-factor.log
  • Retention: 14 days
  • Level: debug

You can override by defining the channel in config/logging.php:

'channels' => [
    'x-factor' => [
        'driver' => 'single',
        'path' => storage_path('logs/x-factor.log'),
        'level' => 'info',
    ],
],

Dashboard

X-Factor includes a read-only web dashboard to browse issues. Visit /{dashboard_path} (default: /x-factor) to access it.

Configuration

'dashboard' => [
    'enabled' => env('X_FACTOR_DASHBOARD_ENABLED', true),
    'path' => env('X_FACTOR_DASHBOARD_PATH', 'x-factor'),
    'middleware' => ['web', 'auth'],
],
  • enabled — Set to false to disable the dashboard entirely.
  • path — URL prefix for the dashboard routes.
  • middleware — Middleware applied to dashboard routes.

Authorization

By default, the dashboard is only accessible when APP_ENV=local. To allow access in other environments, register an auth gate in your AppServiceProvider:

use ArielMejiaDev\XFactor\Facades\XFactor;

public function boot(): void
{
    XFactor::auth(function ($user) {
        return in_array($user->email, [
            'arielmejiadev@gmail.com',
        ]);
    });
}

Features

  • Search — Filter issues by title, exception class, or exception message.
  • Status filters — Filter by status (Pending, Resolving, Resolved, Failed) with count badges.
  • Issue detail — View full exception details, stacktrace, CLI output, and PR links.
  • Retry failed issues — Pick a model and max turns, then re-queue with one click.
  • Resolution progress — Blue callout with spinner for pending/resolving issues.
  • Auto-refresh — Polling toggle reloads the page every 60 seconds.
  • Dark/light theme — Toggle persisted in localStorage.
  • No build step — Uses Tailwind CSS via CDN.

Security Considerations

  • HMAC Verification — Webhook payloads are verified using HMAC-SHA256 (Nightwatch) or Bearer tokens (Bugsnag). Always set X_FACTOR_WEBHOOK_SECRET in production.
  • No Shell Injection — CLI commands are built as arrays and passed to Laravel's Process facade.
  • Environment Whitelist — By default, X-Factor only runs in production and staging.
  • Git Worktree Isolation — The AI never runs in your production working directory.
  • Draft PRs — PRs are created as drafts by default, requiring human review before merge.
  • API Keys — Never stored in config files. Always loaded from environment variables.
  • Autonomous Permissions — Claude Code runs with --dangerously-skip-permissions for unattended operation. Always review generated PRs before merging.
  • Recursion Guard — The exception listener prevents infinite loops if X-Factor's own operations trigger exceptions.

Security Model

  • Curated tools — Claude can only use 6 tools: read_file, write_file, edit_file, list_directory, search_files, and run_command.
  • Path traversal protection — Every file operation validates that the resolved path stays within the git worktree.
  • Command allowlist — The run_command tool only allows configured commands.
  • Worktree isolation — Same as the CLI driver.
  • Max turns — The agentic loop is bounded by max_turns.

What X-Factor Can and Cannot Fix

X-Factor requires a healthy, running Laravel application to function. The queue worker must be alive, the database must be reachable, and Laravel must be able to boot.

What it CAN fix

Any exception that occurs while the app is still running and the queue worker can process jobs:

  • Undefined variables / properties — ErrorException: Undefined variable $foo
  • Type errors — TypeError: Argument #1 must be of type string, null given
  • Bad method calls — BadMethodCallException: Method does not exist
  • Missing models — ModelNotFoundException: No query results for model
  • Query errors — QueryException: Column not found
  • Validation logic errors — incorrect rules, missing fields
  • Authorization / authentication bugs — misconfigured gates, policies, guards
  • Route and controller errors — wrong HTTP methods, missing parameters
  • Logic errors — RuntimeException, DomainException, off-by-one mistakes

What it CANNOT fix

  • PHP syntax errors (ParseError) — Broken syntax prevents Laravel from booting.
  • Fatal errors that kill the process — OutOfMemoryError, segmentation faults.
  • Infrastructure failures — Database is down, Redis is unreachable, disk is full.
  • Errors in X-Factor itself — The package cannot fix its own bugs.
  • Environment / configuration issues — Missing .env values, wrong file permissions.
  • Issues requiring human judgment — Business logic, UX decisions, performance tuning.

The key insight: X-Factor self-heals the same category of bugs a developer would fix after seeing an alert: a typo, a missing null check, a wrong query. The app is running, the error is logged, and the fix is a small code change. That's the sweet spot.

Troubleshooting

CLI tool not found

Make sure claude or opencode is in the PATH of the user running the queue worker. Run which claude to verify.

Jobs timing out

Increase X_FACTOR_PROCESS_TIMEOUT and ensure your queue worker's --timeout flag is set higher than the process timeout.

Duplicate PRs

Check your debounce window (X_FACTOR_DEBOUNCE_MINUTES) and verify the fingerprint constraint is working. Run php artisan x-factor:status to see active issues.

Webhook returning 403

Your webhook secret doesn't match. Verify X_FACTOR_WEBHOOK_SECRET matches the secret configured in your monitor service.

Dry run mode

Enable dry run to test without executing the AI:

X_FACTOR_DRY_RUN=true

Check storage/logs/x-factor.log for output.

Issues stuck in "resolving" status

Run x-factor:recover-stale to mark them as failed, then retry from the dashboard:

php artisan x-factor:recover-stale

Schedule the command hourly to prevent build-up (see Recommended Schedule).

Infinite loop with exception listener

The recursion guard should prevent this. Check that you're not running X-Factor in an environment where database operations consistently fail. Run php artisan x-factor:status to inspect the state.
